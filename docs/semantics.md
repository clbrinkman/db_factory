# 企业数据仓：实体语义与大规模血缘设计

本设计遵循用户描述的内部环境，不套用通用数仓分层定义。当前预览是模拟数据原型，没有连接企查查内部数据平台或数据库。

## 1. 语义约定

| 数据概念 | 三维实体 | 约束 |
| --- | --- | --- |
| 系统 | TiDB 正式档案库 / Hive 数据园区 | Hive 是 ODS、DWD 和 hive_tmp 的上层容器；不把四个名字强制视为同一层级 |
| 数据层 / 数据用途 | 月台、镜像保管区、分析工坊 | ODS = T+1 收货月台，DWD = 镜像保管区，hive_tmp = 分析工坊 |
| 数据库 | 室内命名货架组 / 户外围合堆场 | 收货区采用低位滚筒架，镜像区采用保管柜，分析区采用工作台；户外库与箱内表分开选择，大库分页展示 |
| 表 | 常驻货箱 | 查询不能让源表货箱消失；箱体 ID 对应真实元数据 ID |
| 字段 | 货箱结构卡 | 点击展示字段名、类型、语义别名和字段级血缘 |
| 表分区 | 箱内子包 | 后续接入分区目录时按需展开；当前原型未实现分区钻取 |
| 查询产生的数据副本 | 搬运小包裹 | 与表货箱分离，包裹携带 source_table_id 与 run_id |
| 查询 / 同步 / 加工运行 | 工人、车辆及作业单 | 状态来自任务事件；动画不是数据已经搬迁的证据 |
| 文档目录 | 层级导航 | contains 关系不等于数据依赖，目录父子层级不自动生成血缘 |

TiDB 和 Hive 是系统类型，ODS / DWD 是用户描述的数据层，hive_tmp 是分析库。UI 顶层区分 TiDB 与 Hive，再在 Hive 园区内导航 ODS、DWD、hive_tmp。元数据分别存 engine、environment、layer、database，不强迫这些概念成为同一个数据库层级。

## 2. 四区含义

- **TiDB：正式库。** 本分析界面从中读取允许访问的元数据或副本，不在预览中提供正式库修改动作。
- **ODS：T+1 同步层。** 展示数据截至时间、同步批次和来源；动画不能暗示实时同步。
- **DWD：ODS 的镜像。** 不把它描述为必然完成清洗、标准化的层。模拟数据保持镜像两端字段一致；接入时以真实镜像规则为准。
- **hive_tmp：可删改分析库。** 后续可承载建表、加工和删除；当前只模拟读取副本，没有执行 SQL，也没有实现数据库写操作。

## 3. 当前原型已实现

- 12 个模拟库、2,404 张模拟表、2,003 条模拟血缘，包含新增的两个户外示例库。数量用于交互验证，不代表真实业务规模。
- 四区总览只显示每库的少量真实模拟表，明确显示“当前展示 / 全库数量”。
- 库内每页展示 12 张表；支持表名、中文描述、字段名的全目录检索。
- 可点击货架进入库、点击货箱或目录按钮选择表。
- 选中表可查看字段、直接上下游和文档目录层级。
- 血缘按上游、下游、双向及 1–3 跳展开；三维子图最多 24 个节点、64 条边，超过上限返回折叠数量。
- 同步、镜像、加工关系分别标识；镜像使用虚线，连线包含方向箭头。
- 上下游分别沿有向边遍历，避免经共同下游误把其他输入当作选中表的上游。
- 图遍历维护 visited 集合，遇到环不会无限循环。完整图不预设为 DAG。
- 读取副本的搬运作业不会修改表目录，也不会把源表搬空。
- 无 WebGL 或 CDN 加载失败时，表目录、字段与血缘列表仍可使用。
- 三维建筑按用途区分：TiDB 使用厚壁档案馆及受控入口，ODS 使用收货月台和滚筒架，DWD 使用成对保管设施与封闭柜，hive_tmp 使用工作台、工具墙和操作终端。
- 血缘视图隐藏建筑外壳，保留表货箱与关系，不让建筑遮挡上下游。建筑与货柜的装饰构件不产生额外表或血缘。
- 默认展开完整三维场景，关闭库表目录和详情侧栏。目录、表详情、作业详情按需打开为半透明浮层，支持关闭；透明度可调整。
- 三辆演示叉车分别表示 TiDB → ODS 的 T+1 同步、ODS → DWD 的镜像，以及 DWD → hive_tmp 的分析取料。动作含装载、低位运输、卸货和空车返回。
- hive_tmp 清洗台包含滚筒传送带、处理门架、操作工与搬运工；小包裹加工后改变标记。该变化仅代表演示处理结果，不会改变原表身份或模拟目录。
- 暂停控制统一作用于叉车、工人、传送带与手动搬运作业。浏览字段和打开透明浮层不重置叉车循环。
- 作业运动为演示时间，既不代表实际调度时间，也不表示 ODS 在实时同步。叉车路线与清洗处理使用独立的语义。

## 4. 户外场景与运动验证

### 2026-10-10 户外数据接入园区

新增户外区域位于室内叉车作业区之外；“户外”按钮可聚焦该区域，再次点击回到全景。保留默认隐藏、按需打开的透明浮层。户外映射是可交互原型，不是对企查查内部真实架构的断言。

| 实体 | 对应语义 | 点击结果 |
| --- | --- | --- |
| 来源登记站 | 企业、司法、知识产权的示例来源；不是数据库 | 来源说明，进入原始采集库或来源表 |
| C-01 采集车 | 一次采集任务，载货箱是批次副本 | 来源、目标、当前装载/登记/校验/交接/返程阶段 |
| 围合原始堆场 | `demo_raw_capture` 示例数据库 | 库目录；内部三个常驻表货箱可查看字段 |
| 质检站 / 跨车道门架 | 必填项、记录标识和来源完整性校验 | 规则说明、隔离库与异常表入口 |
| 异常隔离堆场 | `demo_quarantine` 示例数据库 | `rejected_records`，包含 `rule_id` 与来源追溯字段 |
| 待交接月台 | 通过质检的批次与未知下游之间的交接边界 | 显示正式入库规则尚未映射，不自动写入 TiDB |

新增表的字段为 `record_id`、`source_ref`、`batch_id`、`payload`；异常表另有 `rule_id`。三张原始表分别为 `company_payload`、`judgment_payload`、`patent_payload`。三条原始表 → 异常表的派生血缘明确为模拟、未核验；没有虚构原始采集表到 TiDB 的已确认血缘。只有规则结果与批次在任务语义上流动，原始表货箱始终存在。

采集车运行在 z=23–27 的闭合单向环线，两个半圆转弯连接去程与返程；室内叉车路线仍在 z=6.4–8.6。静态人员位于人行侧，检验门架的两根立柱位于车道两侧，不阻断车辆。暂停统一作用于户外采集车、室内叉车、工人和清洗台。此版是单辆户外车的几何路线演示，尚未实现多车交通调度、真实采集、质检规则执行或数据库写入。

二维兼容视图新增独立户外平面视图，使用相同的采集车辆模型时间函数，可切换室内/户外、暂停、打开来源和作业说明、进入对应库表并查看血缘列表。仍明确显示“二维兼容视图 / 三维未启用”，不提供虚假的三维相机或三维血缘画面。

验证更新：纯模型检查共 22 项通过；场景图/DOM 检查覆盖库缺失、WebGL 创建失败和成功初始化三个分支，检查户外来源→表→异常血缘跳转、户外切换、暂停、血缘视图隐藏户外建筑，以及 120 秒仿真中的车辆与静态设施净距。测试曾发现质检门架立柱位于行驶线上，现已改为道路两侧并复测通过。没有进行实际浏览器像素渲染验收；Three.js 场景图与替代渲染器通过不代表真实 GPU 画面已经验证。

### 2026-10-10 叉车动作修订

- 三辆车各占一个互不重叠的装卸作业区，ODS 与 DWD 的接收口、发出口分开。每区只有一辆车；这不是任意数量车辆的通用避障算法。
- 车身、货叉、载荷一起计入保守水平包络，半径为 1.32 场景单位。相邻路线中心扫掠范围至少间隔 3.3，扣除两车包络后净距至少 0.66，大于设定的 0.6 安全余量；不依赖发车错峰来避免穿车。
- 叉车缩放到人物与装卸空间允许的尺寸，轮胎采用无方向纹理的圆柱，不再施加错误轴向旋转，也不在停车时重置轮角。
- 取放流程拆成等待、低叉对位、抬升、直线倒退离位、倒车弧线转向、前进运输、弧线入位、对准、落叉交付、空车退出与返回。车身朝向由曲线切线及前进/倒车状态决定；换向前减速到零，不瞬间掉头。
- 副本在装卸口与车叉之间交接，交接帧的世界坐标、朝向和高度一致。表货箱始终保留；这些装卸副本不是表本身。
- 静态货车移到独立停车区；三条运输路线避开货架、建筑立柱与清洗台。清洗动作及透明浮层保留。
- 二维兼容视图使用同一套路线/作业阶段，显示“二维兼容视图 / 三维未启用”和失败类型；隐藏其不支持的三维能力，库表目录与字段/血缘列表仍可查看。该模式不是完整三维呈现。

验证：`check-warehouse-catalog.cjs` 的 20 项检查通过，覆盖目录语义、扫掠范围、全阶段位置/朝向/抬升连续性、倒车方向、低位运输及副本交接。`check-warehouse-runtime.cjs` 在 jsdom 中使用 Three.js 实际几何和替代渲染器，验证真实车模包络、120 秒仿真中的静态障碍物净距、轮胎安装角保持、暂停与视图切换；另分别模拟库缺失和 WebGL 创建失败。替代渲染器不绘制像素，这些检查不构成浏览器/WebGL 画面验收，也不能确定用户当前打开的预览是否成功进入三维模式。未绕过先前的浏览器安全限制。

运行几何/DOM 检查需 `jsdom@26.1.0`、`three@0.160.1`，可通过 `NODE_PATH` 指向安装目录；目录纯模型检查无外部依赖。后续若增加同一区内车辆数量，应引入占用区预约/让行调度并重新校验扫掠体，不能只增加动画相位偏移。

## 5. 大规模真实环境如何接入

当前所有模拟元数据在内存中，不能据此宣称已验证真实全库性能。生产实现建议采用“元数据服务负责查询，三维层负责有限范围展示”。

### 元数据身份

推荐独立于显示名的稳定 table_id，并保留以下维度：

```text
table_id
system_id / engine / environment / layer
database / schema / table_name
display_name / aliases / semantic_entity_id
owner / document_path / source_reference
snapshot_at / observed_at / schema_version
```

同一企业实体在 TiDB、ODS、DWD 中对应多个物理表，不应因为名称相同就合并。镜像关系连接物理表，semantic_entity_id 可表达业务上的共同身份。

### 血缘证据

```text
edge_id / source_table_id / target_table_id
edge_type: sync | mirror | derive
field_mappings
job_id / run_id / transform_reference
evidence_type / evidence_reference
valid_from / valid_to / observed_at
verification_state
```

单独维护 key_relation，表达主外键或候选关联键；它不自动成为 lineage_edge。字段名相似度只能提出待核验候选，不能直接把推测变成可信血缘。

### 服务接口草案

| 接口 | 返回内容 |
| --- | --- |
| GET /catalog/summary | 分区、库数量和可见性汇总 |
| GET /databases?zone=&cursor= | 当前分区的库摘要 |
| GET /tables?database_id=&query=&cursor= | 当前分页表目录，使用服务端搜索 |
| GET /tables/:id | 表结构、别名、目录引用、批次时间 |
| GET /lineage?table_id=&direction=&depth=&node_limit=&edge_limit= | 有预算的局部图、折叠计数、后续展开游标 |
| GET /lineage/fields?table_id=&column_id= | 指定字段的映射与证据 |
| GET /runs?table_id=&cursor= | 真实作业状态，驱动人物与车辆动画 |

使用稳定排序和游标分页；搜索取消旧请求，避免延迟返回覆盖新选择。场景切换按 ID 复用模型，卸载不可见实例；采用实例化渲染和不同细节级别时，应继续保留可点击实体到真实表 ID 的映射。

### 图算法边界

- 局部探索：基于入边、出边索引的有界 BFS；限制跳数、节点数、边数、查询时间。
- 环依赖：需要展示完整环时先求强连通分量，折叠后再做拓扑排序或分层布局。
- 全局鸟瞰：按用途区、库、业务域聚合；不把全库所有表和所有边同时送入场景。
- 高出度节点：展示聚合节点与剩余数量，用户继续展开；截断必须可见。
- 布局稳定性：保存逻辑位置和用户导航上下文，新增血缘不应让整个仓库重新洗牌。

## 6. 下一步的数据需求

首个真实试点只需脱敏元数据：库表目录、字段结构、已有表级与字段级血缘、文档目录及来源说明。不需要读取 TiDB 全量业务记录。优先选一条 TiDB → ODS → DWD → hive_tmp 的真实链路，再扩到有多来源关联与跨业务复用的链路。

验收应覆盖：稳定 ID、目录一致性、镜像规则、字段映射证据、循环依赖、高扇出截断、历史版本、权限过滤、搜索分页和任务动画与真实状态的一致性。
